## 1. 为什么「答得不错」不是评测

你刚给自己的 RAG demo 补了 20 个常见问题，全都答得漂亮，于是你在周报里写下「检索质量良好」。这句话里有三个漏洞：这 20 个问题是你临时想的，没有一份固定的「卷子」；判「答得好不好」的人是你自己，没有固定的「判分标准」；这套流程你只跑了一次，没有「可重复执行」的机制。一句话：你没有评测，你只有印象。

评测的三个必需品是：**固定样本、固定口径、可重复执行**。缺任何一个，剩下的都只能叫感觉。

在动手写评测脚本之前，先接受一个分层模型，它是全文的骨架：

- **检索层**：该找的 chunk 找到了吗、排在第几。
- **生成层**：答得忠不忠实、有没有编。
- **端到端与业务约束**：用户视角的整条链路，以及「绝对不许发生」的事。

核心论点一句话：**先定位到层，再谈优化**。拿端到端效果去调检索，是最常见的南辕北辙——生成端答错，可能是检索没找到，也可能是模型没用好找到的内容；混在一起，你永远不知道改哪一层。

还要分清「离线指标」与「线上效果」的分工。离线指标回答「这一版比上一版好在哪」，线上效果回答「真实分布长什么样」，两者互相不能用对方替代。真实日志是评测集的**来源之一**，但日志不能直接当评测集——用户问什么，不等于你该考什么。这里先埋一个钩子，第 6 节再展开：评测最贵的成本不是写脚本，是设计和维护评测集；只跑一次的评测，三个月后必然变质。

## 2. 评测集：整篇文章的地基

先想清楚一条样本长什么样：查询（query）、期望命中的目标集合、难度/类别标签、是否可回答。有两个字段容易被新手省掉，省掉就埋雷。

第一个是「期望命中」必须是**chunk 级的稳定标识**，不能是「第 3 条文档」这种位置描述。这就是本文的第一个硬点：**稳定 chunk id**。如果每次重建索引都换一批随机 uuid，那么历史评测结果全部作废，逐条对比失败样本也无从下手。id 应当由「文档标识 + 分块序号 + 内容指纹」这类可复现规则派生。这不是我一个人的洁癖——公开工程实践里，有人把 ground-truth chunk ID 随基准集一起版本化 [W22]，也有人强调语料去重、切块参数、embedding 模型版本都要固化下来才能复现 [W21]。

第二个是「是否可回答」必须分开标注：带答案的问题和无答案的问题要分开算，否则指标会被无答案样本污染。

评测集有三种来源，代价各不相同：从真实日志里挑真问题，分布真实，但需要人工标注期望结果；从文档反写问题，覆盖可控，但会偏向「文档里写了什么」；用模型合成问答，成本最低，但有循环论证风险。三者可以混用，但必须标注来源，因为不同来源得出来的结论不能直接对比。如果暂时没有自己的评测集，公开检索基准可以当起点：BEIR 提供异构检索任务与预处理数据集 [W14]，MTEB 论文摘要给出的口径是覆盖 8 类任务、58 个数据集、112 种语言并附公开榜单 [W15]。但注意两点：一是榜单分数时效性极强、本文一个榜单分数都不写；二是别人的基准只能做起点，最终要换成贴近你自己业务分布的自建评测集。

本节最关键的是这份**自欺清单**：① 用同一个模型生成的评测集去评这个模型 = 循环论证；② 没有 holdout、在测试集上调参，报出的分数只是过拟合；③ 评测集只覆盖「好回答的问题」，没有无答案/越界问题，指标虚高还掩盖真实缺陷。对应一条可执行纪律：**调参只许看训练/开发集，holdout 集在出报告前不许再跑。**

## 3. 指标：Hit@K、Recall@K、MRR 各自在回答什么

四个常用指标，一句话切开：

- **Hit@K**：前 K 条里**至少命中一个**相关结果的查询占比，等价于 trec_eval 里的 success [W01]。
- **Recall@K**：相关结果被找回的比例；多个相关目标时才有区分度，单目标时退化等价于 Hit@K [W02]。
- **MRR**：第一个相关结果排名的倒数（第 1 位记 1、第 2 位记 1/2…），跨查询取均值 [W03]。
- **nDCG**：用分级相关性做增益、对排名做折扣、再按理想排序归一，适合有「非常相关/一般相关」之分时 [W04]。

选指标之前先问一句：**我的场景里「错」的代价是什么？** 单条相关、只看「找到没找到」就报 Hit@K；看重「找到了但排得靠后」就加 MRR；有分级相关性才上 nDCG。下面这段代码可以直接跑，把 Hit@K 与 MRR 落成数字（nDCG 只给实现，未在此处调用）：

```python
"""检索指标的最小实现（纯标准库，可直接运行）。"""
import math

def hit_at_k(retrieved, golds, k):
    return int(any(d in golds for d in retrieved[:k]))

def mrr(retrieved, golds):
    for i, d in enumerate(retrieved, start=1):
        if d in golds:
            return 1.0 / i
    return 0.0

def ndcg_at_k(retrieved, grades, k, gain=lambda g: g,
              discount=lambda r: 1 / math.log2(r + 1)):
    cut = retrieved[:k]
    dcg = sum(gain(grades.get(d, 0)) * discount(r) for r, d in enumerate(cut, start=1))
    ideal = sorted(grades.values(), reverse=True)[:k]
    idcg = sum(gain(g) * discount(r) for r, g in enumerate(ideal, start=1))
    return dcg / idcg if idcg else float("nan")

retrieved = ["d1", "d2", "d3", "d4", "d5"]
print("Hit@5 =", hit_at_k(retrieved, {"d5"}, 5))      # 1：找到了
print("MRR   =", mrr(retrieved, {"d5"}))              # 0.2：找到了但排在第 5
print("Hit@1..5 =", [hit_at_k(retrieved, {"d5"}, k) for k in (1, 2, 3, 4, 5)])
```

注意输出里的 `[0, 0, 0, 0, 1]`：**K 变大，Hit@K 单调不减**。这引出 K 怎么定——K 不该是「随手取 5」，而该对齐下游 prompt 里真正会塞几条：生成端最多只塞四条，Hit@4 才是有工程意义的口径；报 Hit@10 好看，但没有落地含义。跨 K 比较等于拿两份不同的卷子比，毫无意义。

最后一个陷阱是**粒度**：指标算在 chunk 级还是文档级，结论可能完全相反（chunk 拆得越细，命中越容易好看）。所以报告必须写明粒度，同一项目跨版本比较时粒度不能变。对应地，同一个检索系统，我建议同时报 Hit@K 与 MRR 并附样本条数——「找到了但排得靠后」和「压根没找到」是两类问题，前者动重排/融合，后者动切块/embedding。

## 4. 样本量与报告口径：16 条样本差 1 条是 6 个百分点

先算一笔硬账：样本只有十六条时，一条就占十六分之一，也就是 6.25 个百分点。这意味着两件事。第一，样本量小的时候**不许报一位小数**——报了就是自曝虚精度。第二，结论必须带样本规模一起说：「0.8」和「十六条里命中十三条」是完全不同的可信度。

比「报一位小数」更普遍的是「报最好值」：跑三次挑最高的一次写进报告，这是最常见的自欺。正确口径是「样本规模 + 跑几次 + 若多次则给区间或最差」。**「一次回归」与「连跑多次取区间」是两种验证强度**，混着说等于夸大；只跑了一次，就老老实实写「单次回归结果」。

下面这段代码演示小样本下区间怎么算，用 scipy 的 `binomtest`：

```python
from scipy.stats import binomtest

r = binomtest(13, 16)  # 16 条命中 13 条
for m in ("exact", "wilson"):
    lo, hi = r.proportion_ci(confidence_level=0.95, method=m)
    print(f"{m:8s} 13/16 -> [{lo:.4f}, {hi:.4f}]")
```

输出是 scipy 的 `proportion_ci` 给出的两档区间 [W18]：`exact` 为 `[0.5435, 0.9595]`、`wilson` 为 `[0.5699, 0.9341]`。看到没有——13/16 折成 0.81 这个点估值，配上 95% 区间后宽度是 0.4 的量级；而两位小数隐含 ±0.005 的精度，数据根本支撑不了。另外，12/16 与 13/16 的区间大幅重叠，所以「涨了 6 个点」在 n=16 时不能当结论，只是抽样噪声。

这些口径有公开的方法学出处：比例的置信区间方法（Wilson、Agresti–Coull）见 NIST 手册 [W17]，scipy 的 `proportion_ci` 见官方文档 [W18]，评测基准的方差决定「性能差异是否有意义」这一点有专门论文 [W16]，面向 LLM 评测的「每个输入跑 k 次再 bootstrap」配方有工程博客 [W19]。两句诚实细节必须说清：① scipy 的 `proportion_ci` 合法口径只有 exact / wilson / wilsoncc 三档，正态近似与 bootstrap 是我自己实现的，不是 scipy 提供的；② bootstrap 的前提是样本近似 i.i.d.，如果评测集是分层配额（如 8 条事实型 + 8 条越界型），区间会偏窄，应分层报告。

跨版本对比的公平条件是：同一评测集、同一 K、同一粒度、同一 chunk id 映射；**不同时改两个变量**，否则涨了也不知道是谁的功劳。由此引出消融：一次只改一层，看增益落在哪——如果改了 query rewrite 收益很小，基本说明瓶颈在分块与 embedding 层，继续在改写层打磨是白费力气。

## 5. 生成侧：忠实度与幻觉怎么测，以及为什么别急着上模型裁判

先分清三件事：**检索侧指标**（找到没找到）、**忠实度**（回答是否只用了检索到的内容）、**正确性**（回答是不是对的）。三者的失败原因不同，混成一个「准确率」就再也定位不到问题。

我的主张是**规则校验优先于模型裁判**：把结构化来源（价表、参数表、政策里的枚举值）做成值池，反查回答里出现的数字/金额/枚举值是否落在池内。它可复现、无裁判方差、失败可逐条定位，而且跑起来几乎不花钱。但要说清适用边界：这种「合法取值集合反查」只对**可枚举的结构化事实**有效，自由文本类断言它管不了。下面这段是它的最小示范：

```python
"""合法取值集合反查（作者实践，仅作方法示范）。

把合法取值做成集合，反查回答里的金额是否都在集合内。
"""
import re

AMOUNT_POOL = {"29", "59", "99", "0.29"}  # 价表中真实存在的金额（示例值）

def off_pool_amounts(answer):
    tokens = re.findall(r"\d+(?:\.\d+)?", answer)
    return [t for t in tokens if t not in AMOUNT_POOL]

print(off_pool_amounts("套餐 59 元，超出后 0.29 元/MB 计费。"))  # []：全部在池内
print(off_pool_amounts("套餐 39 元，超出后 0.29 元/MB 计费。"))  # ['39']：价表里没有，报警
```

关于来源要说清楚：「先跑规则」在公开实践里有对应——LangChain 官方页面把确定性规则当作 first pass [W20]，也有工程做法在检索 sanity check 失败时直接短路、不花裁判的钱 [W24]；「连跑多次看通过率」也有公开出处 [W19][W23]。但「用合法取值集合反查回答里的数字/金额」这个具体做法，我检索后没有找到把它讲清楚的公开来源——所以它只以我的个人实践身份出现，不是业界共识。

LLM-as-judge 不是不能用，而是**别急着把它当默认答案**。已知偏差有论文级证据：位置偏差、冗长偏差、自我增强偏差被明确命名并测量 [W11]；只要改动候选答案在上下文里的出现顺序，就能操纵裁判结论 [W12]；相关信息在上下文里的位置本身就会影响模型表现 [W13]。如果要用，纪律是：固定裁判模型版本、固定 prompt、固定温度、抽样人工复核、并**报告裁判一致性**而不是只报分数。

框架的现状也可以一句话说清：以 ragas 为例，截至 2026-09-17 本文核稿时 PyPI 上的最新版是 0.4.3、许可 Apache-2.0 [W07][W08]，必装依赖里含 openai / langchain / instructor [W09]，默认强依赖一个外部 LLM 当裁判——但框架同时提供非 LLM 指标，本机实测锁好可选依赖后，可以在完全离线、无任何 API key 的环境跑出分数；而 Faithfulness 这类指标不注入裁判模型时会直接报 `LLM is not set`。两条实测得来的诚实细节：① 非 LLM 指标测的是「像不像」而不是「对不对」，与集合反查的字段级约束不是一回事；② 用默认解析安装 0.4.3 会因 langchain-community 版本冲突导致 `import ragas` 失败，把 `langchain-community` 锁到 `<0.4` 才恢复，照抄之前先锁版本。

最后给一个把评测变成资产的动作：**失败样本归档**。每次评测把「未命中的查询 + 期望目标 + 实际返回」落成一份文件，按类别归档；下次改版先看这份文件有没有变小。这是从「一次性打分」变成「持续资产」的关键一步。

## 6. 业务约束与回归：把「绝不许发生」写成断言

统计指标是「比例」，业务约束是「有没有」。把「不许答出未确认的办理结果」「不许编出价表里没有的价格」「不许在无依据时给出确定性承诺」写成**可自动断言的回归用例**，用「断言条数 + 违规数」这种表述——它比「准确率百分之百」更有说服力，因为它可被证伪：多跑一条新样本，就可能把它拉下来。

把指标与断言接进 CI：回退超过阈值就拦住合并。阈值定多少？依据是历史波动，不是理想值。指标波动时先怀疑三件事：评测集变了吗、chunk 变了吗、模型版本换了吗——而不是先怀疑自己写的算法。

评测集的版本管理同样要进仓库：样本文件随代码一起提交，改动留痕（哪一版加了哪些样本、为什么加）。这里藏着面试官/同事必问的一句：**「你这套评测能给我看看吗？」** 拿不出来，等价于没做。可执行的动作是：回自己项目里，把评测脚本、样本文件、输出日志三样路径记下来。

最后是成本取舍：「评测太慢就没人跑」是现实。建议分层——秒级冒烟（快、规则类，每次提交跑）、分钟级回归（每次合并跑）、小时级全量（慢、需要模型调用，按天或按版本跑）。

## 7. 速查表与自检清单

速查表可直接贴进项目 README：

| 层次 | 回答什么问题 | 常用指标或做法 | 什么时候用 | 什么时候会骗你 |
|---|---|---|---|---|
| 检索层 | 该找的找到没、排第几 | Hit@K、Recall@K、MRR、nDCG | 每次改检索都要跑 | K 变大必然变好；粒度口径变了结论会翻转 |
| 生成层 | 答得忠不忠实、有没有编 | 忠实度、合法取值集合反查、规则断言 | 生成端改动后 | 把「像不像」当「对不对」 |
| 端到端与业务约束 | 整条链路 + 绝不许发生的事 | 业务断言 + 违规数 | 每次发布前 | 把「没有样本」当「没有问题」 |

落地目录五件套：评测集文件 / 跑批脚本 / 输出结果（带时间戳）/ 报告 / 失败样本归档。

自检清单，逐条勾：

- 我的评测集有固定样本与稳定 chunk id。
- 我有 holdout，且没在上面调过参。
- 我知道我的 K 为什么是 K。
- 我报告时带了样本规模。
- 我区分了「一次回归」与「连跑多次」。
- 我的忠实度校验不依赖另一个模型当裁判（或者我说明了它的使用纪律）。
- 我把「绝不许发生」写成了断言。
- 我能拿出评测脚本与原始输出。
- 我每次改版都对比了失败样本归档。

RAG 的差距不在于你调了什么参数，而在于当别人问「你怎么知道它变好了」的时候，你能不能拿出一份别人可以重跑的卷子。
