## 一、服务端写了两行，客户端只知道「失败」

先看一个现场，三份材料并排放：

- 服务端的写入日志里，同一个业务动作出现了**两行**；
- 客户端进程的退出码是 1，而且是被 `taskkill /F` 直接打死的——没有异常栈，因为它根本没机会打印；
- 而如果这一步要交给人接手，工单表里关于它的那行「结果未知」，只能是**一条空行**。

前两条不是编的：我在本地隔离环境里做了一次受控故障注入（本项目实测，不接任何真实外部服务）——一个用标准库 `http.server` 起的 mock 订单服务端，一个 1 秒级短超时的 `httpx` 客户端，在「服务端已经落盘、响应还没回到客户端」的那一瞬间把客户端进程杀掉，然后用同一个业务动作重跑。结果是：服务端留下了两条 `row_id` 不同的记录，而朴素日志（只在拿到响应后才写）最后只剩 attempt 2 的那一条成功记录，**第一次执行在磁盘上一点痕迹都没留**——事后你根本无法区分「它没发生过」和「它发生过但你没看见」。

为什么这件事重要：这一档 bug 的根子不在「退避参数没调好」，而在这一处——失败发生的瞬间，客户端拿到的信息根本不足以回答「这一步到底执行了没有」。而你的重试代码，在它自己都不知道答案的时候，已经替你选了一个。

我先把这个实验能证明和不能证明的边界说清楚：它证明了「写入完成、响应未返回」这一种失败模式下，无键重试确实会重复副作用；它没有覆盖网络分区、并发双写、幂等键过期、跨服务部分失败——这些没测过的，我不会假装测过。全文要回答的问题就一个：**一次工具调用失败之后，你怎么知道它是「没发生过」还是「发生过了但你没看见」？而在你不知道的时候，你的代码做了什么？**

下面是这个现象的极简可复现版本（真正的实验用服务端 `write + fsync` 后写 signal 文件来锚定 kill 时机，实测「看见信号 → 发出 kill」的间隔为 0.382–0.471（单位：秒），第一次跑还踩了个信号文件前缀拼错的坑，导致 kill 在服务端写入后 20 秒才发出；修好后重跑，正文数字来自修正后的运行）：

```python
# mock_server.py —— 先落盘、再挂起不响应
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer
import json, time

ROWS = []

class Handler(BaseHTTPRequestHandler):
    def do_POST(self):
        n = int(self.headers.get("Content-Length", 0))
        ROWS.append(json.loads(self.rfile.read(n)))   # 副作用：写进表
        print("WROTE row:", ROWS[-1]["row_id"])
        time.sleep(30)                                 # 超过客户端超时：从客户端看等价于响应丢了
        self.send_response(201); self.end_headers()
        self.wfile.write(b"ok")

ThreadingHTTPServer(("127.0.0.1", 18761), Handler).serve_forever()
```

```python
# client.py —— 短超时 + 重试，不带幂等键
import httpx, uuid

for attempt in (1, 2):
    try:
        r = httpx.post("http://127.0.0.1:18761/order",
                       json={"row_id": str(uuid.uuid4())}, timeout=1.0)
        print(attempt, r.status_code)
    except httpx.ReadTimeout:
        print(attempt, "timeout")
```

跑起来你会看到服务端打印两次 `WROTE row`，客户端打两次 `timeout`——副作用翻倍，而客户端从头到尾只知道自己「失败」了。

## 二、三态，不是两态：判断依据是「有没有越过执行起点」

我们习惯把失败分成「可重试 / 不可重试」两档。这个二分的问题不在于不够精确，而在于它把第三档强行塞进前两档；塞错方向的两个后果并不对称：塞进「可重试」，你会重复执行；塞进「不可重试」，你会把没做的事当成做完了。

正确的分法是三态：

- **A 明确未生效**：请求没到，或服务端在开始执行之前就拒绝了（参数校验失败、无效密钥、限流）——可以放心重试。
- **B 明确已生效**：拿到了成功响应——继续。
- **C 不确定**：请求发出去了，但响应没回来，或者回来的信息说明不了到底执行没有——**这是本文要抢回来的那一档。**

要把「执行到哪一步」变成可落地的坐标，得先给相位起名字。本文把一次调用切成五段：P0 参数/序列化（服务端不会开始执行）、P1 连接建立前（DNS 失败、连接被拒、TLS 握手失败）、P2 已发出但未确认开始执行（发送途中连接被重置、网关拒绝、限流）、P3 服务端可能已开始执行而响应未回到客户端（读超时、连接中断、进程被杀、响应体截断）、P4 收到响应但本地处理失败（解析失败、本地落盘失败）——**这套划分是本文主张，不是官方术语**。P3、P4 是确定的不确定态，P2 是灰度区；后文说「P3 的一种形态」、工单 `phase` 字段填 P0–P4，指的都是这套坐标。

判断某一档的标尺不是异常类名，而是「请求有没有越过服务端的**执行起点**」。这条判据有官方落点：Stripe 的幂等层只在「endpoint 开始执行之后」才保存第一条请求的结果；而参数校验失败、无效密钥、限流这类「执行之前」的失败，官方明说「没有任何 API endpoint 开始执行，这些请求可以重试」[W11][W12]。也就是说，「执行起点」不是一个比喻，是真实存在的判据。

为什么按异常类型分流在边界上必然漏？因为同一个异常类可以横跨不同的相位。`ConnectionError` 既可能是「连不上」（安全），也可能是「发完了等响应时连接被重置」（危险）；超时也分 connect timeout 和 read timeout。决定该不该重试的信息，不在异常对象里，而在「请求走到了哪一步」里——而这一步，通常只有服务端知道。

把这个信息拿不到时的正确答案说破：**不是猜，是把「拿不到」显式建模成第三态。** 分布式系统里早就有两个固定的词指向这件事——支付 API 把返回 500 的请求结果定性为 `indeterminate`（不确定）[W17]；分布式事务（XA/2PC）把「已 prepare 但尚未 commit」的事务叫 `in-doubt`（存疑）[W35]。两个领域、两个词，说的是同一件事：有一类结果，机器自己判断不了。本文用中文「结果不确定」来称呼它。

## 三、框架的默认值，把你最怕的那一档设成了「自动重试」

接了 LangGraph 的 `retry_policy`，不等于这件事就办完了。把它的机制拆开看，问题会自己浮出来。

框架给的是一组固定顺序的机制：retry policy 先判断要不要重试；**只有重试耗尽之后，error handler 才运行**[W02]。这意味着这套机制真正回答的是「失败之后怎么办」，它**没有「不确定」这个分支**——你喂给它的分类信息（异常类型）本身就不足以判断三态。

再看默认值。`default_retry_on` 是一张**排除清单**：除了 `ValueError`、`TypeError`、`OSError` 等一串类型（及其子类）之外，其余异常一律重试[W03]。两个直接后果：

第一，`NodeTimeoutError` 默认可重试[W03][W04]——而读超时正是最典型的不确定态。框架不是疏忽：我在本机隔离 venv（langgraph 1.2.11，非生产环境）里实测了 `NodeTimeoutError` 的继承链，它特意**不经过** builtin 的 `TimeoutError`，源码注释写明这是为了让默认 `RetryPolicy` 把它当可重试。也就是说，「超时自动重试」是框架的有意取舍，不是漏配。

第二，对 HTTP 客户端库，文档里「只重试 5xx」的说法在实际求值上不完整。我在同一份代码路径下对 20 个异常实例逐个求值，结果反直觉：`httpx.ReadTimeout` 判 **True**（重试），`requests.ReadTimeout` 判 **False**（不重试）——同一档次失败，仅仅因为两个库的异常继承关系不同，默认行为就翻转。`requests` 的超时/连接异常继承自 `RequestException → IOError（即 OSError）`，落进了排除分支；`httpx` 的传输异常不继承 `OSError`，落进了「其余一律重试」。判定值是实测，机制解释是我读源码推出来的。

还有最锋利的一条，必须讲清楚边界：超时触发时，框架会「清掉这次失败尝试的 writes」[W05]。清的是什么？**是这次尝试写给图 state 的东西，不是外部系统里已经落地的那条记录。** 我实测过：节点体内先对外部 jsonl 文件 `write + fsync`、再触发超时，结果外部文件 3 行、state 是 `{}`——框架侧看起来「干干净净」，外部副作用一次没少。checkpoint 保证的是「图状态可恢复」，**不是「外部副作用只发生一次」**（这条是本文推论，依据是文档原文的宾语是 writes）。

`error_handler` 是补偿点，不是判据点：它在重试耗尽之后才运行，拿到的是 `NodeError`（`node` + `error` 两个字段），返回 `Command` 可以改 state 并 `goto` 到别的节点——这是 Saga/补偿的位置，也是本文「第三档转工单」的落点。门槛是 `langgraph>=1.2`[W01]，本机隔离 venv 里是 1.2.11，确实有。但限制要一起记住：每个节点最多一个 handler[W07]；超时只对 async 节点生效、sync 节点带 timeout 编译期被拒[W08]；`set_node_defaults` 不被子图继承[W06]。还有一个文档没写、我踩过的坑：handler 的 `error` 形参必须显式标注 `NodeError` 才会被注入，否则运行期 `TypeError`（本项目实测）。

## 四、幂等键装在哪一层：工具层的键位与落盘时机

先讲清「幂等」到底承诺了什么，拿 Stripe 的两种语义做对照最清楚。v1 是「**重放**」：同一键的请求返回第一次保存的状态码与响应体——**包括 500**——也就是「别再执行一遍，我把上次的结果给你」[W09]。v2 是「**续做**」：不重复已经成功的操作，把失败或部分失败的工作继续做完，返回更新后的响应[W10]。两种语义都建立在同一个前提上：**服务端记得住这个键做过什么。** 没有这个前提，幂等只是客户端的一厢情愿。

它为什么正好治「不确定」这一档：不确定态的本质是「我不知道」，而幂等键把「我不知道」变成「**我可以拿同一个键再问一次**」。注意，这个动作不是「再执行一遍」，而是「查询同一个业务动作的结果」——这才是把不确定变确定；「赌它没生效所以重试」不叫处理，叫抽签。

落到工具层，有三条硬要求（本文主张，不是官方规定）：

1. **键在调用前就落盘。** 如果键只活在内存里，进程被杀之后你连「用过哪个键」都不知道，对账无从做起。Stripe 文档没直说这一条，但它要求「重试要用同一个键」[W18]，而「用同一个键」的前提就是键在磁盘上、进程死了还在。
2. **键由业务意图派生，不取模型输出。** 模型每次现生成的随机串会让同一个业务动作在两次尝试里变成两个键。
3. **副作用收敛到一个可去重的写点。** 同键第二次到达时走「已存在」分支，而不是两个写点各自并发落库。AWS 说得更硬：记录幂等 token 和所有相关变更操作，必须构成一个 ACID（原子）过程，否则会出现「记了 token 但没建成资源」或「建成了资源但没记 token」[W25]。

「盖到工具层」到底意味着什么？一次工具调用通常不等于一次 HTTP：建单 → 扣额 → 发通知，三步加本地落盘。HTTP 客户端自带的传输层重试发生在更内层，它们共享同一个键才安全；但如果键是工具函数里每次现生成的，那么外层每重试一次就换一个键，同一次业务动作在网络抖动下会变成两个键、两份记录。**判据一句话：幂等键的生成点必须与「业务动作」的边界重合，并向下透传到每一次网络调用。**

协议层有没有现成位置？MCP 的工具注解里有 `idempotentHint`，语义是「用相同参数反复调用不会产生额外影响」[W32][W34]——但规范明确写整块注解是 hints，且「客户端绝不应该根据 ToolAnnotations 做工具使用决策」[W31][W33]，而且 schema 里**没有任何幂等键字段**（本项目对 2025-06-18 版做了全文检索，`idempoten` 只出现 1 次）。所以「幂等键要盖到工具层」在协议层没有现成位置，**键必须由应用层自己造**——这是本文主张，不是「MCP 规定的做法」。

再看「带键」把上面的实验翻过来的效果（本项目实测）：键在调用前落盘（`sha256("ORDER-C")[:32]`），第二次请求进的是服务端 replay 分支，返回的正是第一次的响应，`attempt_seen="1"`，服务端只有 1 行写入。带键和不带键，差的就是「调用前多落一个键文件」这一行。

键也有寿命边界：Stripe 允许在键满 24 小时后剪掉，剪掉后复用同键会被当成新请求[W13]；AWS 也明说幂等信息不能无限期保留[W29]。所以「同键重查」只在一个有限窗口内有效——这条不是规范，是类比（本文主张），但结论成立：**不确定态必须在键过期前完成对账**，这也是工单要有 owner 和时限、而不只是状态字段的原因。

## 五、降级不是重试：四级阶梯与一条判据

先把两个词分开：重试是**同一个动作再来一次**；降级是**换一个动作**。混在一起最常见的写法是「失败 3 次就换个工具再试」——如果那个工具也会改外部状态，这就等于给同一个业务意图制造了第二个副作用源，而两次副作用之间没有任何键把它们关联起来。

四级阶梯，从最不伤到最伤：

1. 同工具换路径（不同 region / endpoint / 连接池）——**同一幂等键**；
2. 换备用实现（只读源 / 缓存 / 抽样结果）——**前提是不改外部状态**；
3. 降级为「向用户要输入或要确认」；
4. 停止并转人工工单。

越往下走，越不许自动。一条判据贯穿全程：降级路径的第一步先问「这一步会不会产生外部副作用」。会 → **不允许静默降级**，必须带同一个业务动作 ID 走幂等键或直接进工单。这条判据同时解释了为什么「换个模型再生成一次」在只读场景无所谓、在写场景是灾难——模型重跑会给你一个**全新的**内容，但它改变的外部状态不会跟着「重新生成」。

最后是乘数。`max_attempts` × 降级路数 × 并行子任务数 × 每次耗时，才是重试风暴的真实放大倍数。顺序必须是：先定「哪些档允许自动」，再算乘数，最后才调退避与抖动（本文建议）。AWS 把话说得更直白：把重试当瞬时故障的缓解手段，本身建立在「该操作可以无副作用地重试」这个简化假设上[W23]——假设一旦不成立，乘数就是放大的破坏数。

## 六、不确定态的归宿：一张工单，和一条「不许前进也不许后退」的规则

第三档该去哪？去一张有人认领的工单。最小 schema（本文主张，公开来源只提供要素、不提供这份 schema）是这样一组字段：

| 字段 | 含义 |
|---|---|
| `business_action_id` | 业务动作，不是 HTTP 请求 |
| `attempt_id` | 本次尝试 |
| `idempotency_key` | 业务意图派生的键 |
| `phase` | P0–P4 相位 |
| `outcome` | `ok` / `not_executed` / `unknown` |
| `evidence` | 响应快照、时间戳、服务端可见的痕迹 |
| `owner` | 认领人 |
| `deadline` | 与键寿命对齐 |

核心是一条阻断规则：`unknown` 的步骤**不许当作成功继续**（否则下游全部建在一个可能不存在的假设上），**也不许当作失败回滚**（可能已经生效，回滚会造成第二次破坏）。「既不能前进也不能后退」的状态，才是真正需要人接管的状态——这句话比任何重试参数都重要。

人工处置只有三个动作：① 确认已生效 → 补记录，`unknown → ok`，下游放行；② 确认未生效 → 复用**同一个键**重试一次，`unknown → not_executed`；③ 补偿 → 走 Saga 分支（冲正/撤销/通知），并留下补偿本身的凭证。**没有第四个动作叫「再等等看」。**

这不是我一个人拍脑袋的规矩。Stripe 官方对 500 的处理是「结果不确定，在解决原结果之前不要用新键重试」，网络失败用同一把键在原请求后 24 小时内重试，窗口过期则「停止重试并对账」[W17][W18][W19]；分布式事务领域把「存疑」制度化成了人工裁定——必要时由 DBA 覆盖决定 commit 还是 rollback[W36]。注意官方只说了「停止重试并对账」，**没说**「要建工单表、要有 owner」，这两点是我的工程化补充（本文主张），别把它们写成官方要求。

落到 LangGraph 上的接法只是接线、不是教程：`unknown` 分支**不要用 `retry_policy` 表达**（它会重试），用 `error_handler` 返回 `Command(goto="pending")` 或条件边路由到工单节点；想表达「同一节点第 N 次仍不确定就转人工」，可用 `execution_info.node_attempt` 计数（1 起算）。

## 七、落地顺序、反面清单与收口

从最钝的开始，顺序不能反：

1. 给每次工具调用打**相位 + 三态**日志（没有这个，后面全是猜）；
2. 把副作用收敛到单点可去重的写，**幂等键在调用前落盘**；
3. 为 `unknown` 建工单表 + 下游阻断规则；
4. 最后才是退避与抖动参数。

原则一句话：先把「不知道」这件事变成一种状态，再谈重试几次。

反面清单（本文的「别这样做」）：① 按异常类名分流（一长串 `isinstance`）；② 把 5xx 与超时一律当「可重试」（框架默认策略就是这么给的）；③ 幂等键由模型生成、或每次现生成、或只在内存里；④ 重试耗尽直接把图判失败（丢掉补偿分支，也就丢掉了对账线索）；⑤ 把「换个工具再试」当降级。

缺口必须说清：本文的故障注入只覆盖 P3 的一种形态（单进程 kill、本地 mock 服务端），**不覆盖**网络分区、并发双写、键过期、跨服务部分失败；LangGraph 侧只核了 1.2.11 这一个版本。凡是我没验过的，都需要你按自己的环境补测——不存在「装上就不会重复」这回事。

速查表，症状 → 该看哪一档 → 立刻能做的动作：

- 收到两条通知 → 已生效但被重试了 → 找幂等键落盘点；
- 超时但不知道有没有落库 → 不确定 → 停，进工单，用同键重查；
- 一个工具里有三次网络写 → 键没盖到工具层 → 把键的生成点挪到业务动作边界；
- 换了工具还是同一件事 → 静默降级 → 退回「向用户确认」；
- 工单表里只有「处理中」没有「结果未知」 → 三态没建全 → 补 `unknown` 档。

收口一句：重试的前提不是「这个错能不能重试」，而是「这一步有没有可能已经生效」。前两档可以自动化，第三档的正确动作是停下来——不是停下来等，而是停下来把它变成一张有人认领的单子。
